# Unit performance ladder

The protocol and pass rules are in [ADR 0004](../../adr/0004-unit-simulation-architecture.md#performance-ladder). Scenario version 1 uses the sandbox's native-array simulation and the instanced unit mesh the game currently draws (ADR 0016). Units hold position: the build currently applies spawn commands at 30 Hz and fills draw matrices and draws every frame. Movement, targeting, combat and commander AI are not implemented. The seed is stored but no random work occurs. Layout uses the sandbox's compact block placement, small units for the first faction and large units for the second.

Under [ADR 0009](../../adr/0009-slow-frame-regression-cutoff.md), a step is `regressed` when its average frame time median is worse than the comparison by more than both 10% and 0.5 ms, or its current 1% low median is at least 3.0 ms (including exactly 3.0 ms) and exceeds both of those thresholds. The average check is unchanged; the 1% low is still recorded below the cut-off.

Before measuring, read [Issue #97's speed-test finding](../issue-97-speed-test-finding.md), commit the measured sources, close the Editor, set Windows power mode to best performance and leave this PC idle. The Producer reserves the PC: no other Unity run may overlap a ladder. The Player requires a real 1920×1080 borderless desktop with focus. A sandbox without these cannot produce valid measurements; an offscreen render request is not a substitute.

From the repository root, use these two PowerShell commands. The direct Unity command is the only escalated command. The pipe waits for the GUI executable to finish. It generates the scene/scenario and builds both release and development Windows x64 Mono Players without changing Editor Build Settings.

```powershell
& 'C:\Program Files\Unity\Hub\Editor\6000.3.23f1\Editor\Unity.exe' -batchmode -nographics -projectPath "$PWD\Game" -logFile "$PWD\Game\Logs\ladder-build.log" -executeMethod Northwatch.EditorTools.PerformanceLadderBuilder.BuildWindows -ladder-commit FULL_40_HEX_COMMIT_SHA -quit | Out-Null
node tools/unit-ladder.js baseline no
```

Replace `FULL_40_HEX_COMMIT_SHA` with the Producer's full measured commit SHA. Replace `baseline` with `"PR #123"` or `"re-run: reason"` as appropriate. The final argument is the reference-class decision: `yes` only for the ADR's RTX 3050 6 GB and mid-range six-core CPU; otherwise `no`. A pass on other hardware supports trends only. Check the build log before running. Changes to the scenario or harness start a new scenario version/comparison series. A unit mesh change doesn't; it stays in the series (ADR 0016).

The runner refuses uncommitted sources, a build for another SHA, changed source hashes, or changes to sources/hardware during measurement. It runs every step in order, requesting three valid fresh Players within six attempts per step. Each Player warms up for 10 seconds, records 60 seconds and drains delayed timings for two seconds. The preallocated buffer holds one million frames; overflow invalidates the run. Callback timestamps use native Windows QueryPerformanceCounter, sharing the FrameTimingManager clock origin and frequency. Native frame-start timestamps match disjoint intervals between consecutive script callbacks; rendered frames are counted independently. Overlapping timing polls are deduplicated by timestamp; two distinct samples matching one frame invalidate it. Metadata records matched and unmatched sample counts; unmatched samples invalidate the run. Frames after the closed window are ignored during the drain, while delayed window samples still match. Missing samples remain missing after the drain. Setup failures log their reason and exit with code 1; named exceptions in Player logs also invalidate a run.

Raw CSV, metadata, Player logs and development captures stay under ignored `Game/Logs/`. The Player counts physical cores with Windows `GetLogicalProcessorInformationEx`; Unity supplies the CPU model, logical thread count, rendered GPU and memory sizes. The runner reads only GPU description/driver version and Windows product/version/build values from fixed registry locations, which work inside the sandbox without CIM access. It matches the driver to the rendered GPU and rejects missing or ambiguous information. Hardware is checked across attempts and registry values before and after the ladder. No device name or identifier is read. Public entries contain an allow-listed summary with all attempt results, three-run spread and optional timing missing counts. Comparison entries come from the local `main` ref's addition history; update that ref before launching the worktree. A failed step still records its curve; invalid runs, regressions and previously passing steps that fail give the command a nonzero exit code. Every entry is append-only and names the full measured commit; the Producer can commit the entry alone afterward.

For the separate allocation check, after building and with no other Unity run active, run the development Player from PowerShell and wait for it to exit:

```powershell
& .\Game\Builds\PerformanceLadderDevelopment\PerformanceLadder.exe -ladder-units 2000 -ladder-profile -ladder-output "$PWD\Game\Logs\unit-ladder\profile" -logFile "$PWD\Game\Logs\unit-ladder\profile.log" | Out-Null
```

Development captures run at **25 fps** and record the full 60-second window by default. Release measurements remain uncapped (`targetFrameRate=-1`) with the Profiler off. For a short diagnostic, add `-ladder-profile-seconds 10` (accepted range: 10–60 seconds, development captures only). This shortens binary recording; the Player still completes its usual warm-up, 60-second window and drain. Validate a capture change on a short capture before analyzing a full one. No argument-file fallback is used.

After the Player exits, run the Unity batch command with `-executeMethod Northwatch.EditorTools.LadderProfileAnalysis.Analyze` and a separate log. Studio agents use the launcher's `unity_batch` for all Editor runs. Analysis defaults to `Game/Logs/unit-ladder/profile.raw` and writes `profile-summary.txt`. For another capture, pass `-ladder-capture-path Logs/unit-ladder/NAME.raw`; the normalized path must stay inside this project's `Logs/`, and the summary is `NAME.raw-summary.txt`.

Every reader scans all retained frames except the first and last, without striding or early success. Analysis rejects fewer than 200 samples or any managed allocation beneath `Northwatch.Simulation` or `Northwatch.Drawing`. Previously, the uncapped ladder file exceeded Unity's 2,000-frame retention limit: its 1,998 drawing samples covered only about 1.4 seconds at 1,400 fps. At 25 fps, the full window fits: #230 recorded 1,499 drawing samples and 2,998 simulation samples across 60 seconds. Each frame spans at least one 30 Hz tick, exercising the scheduling path; zero-tick frames take a subset of that path. The allocation checks therefore retain their coverage of the simulation/drawing paths and cover more elapsed time. Tests also verify an allocation present in just one interior frame. As before, this is evidence for the recorded workload, not a guarantee against allocations that depend on unrecorded frame counts.

Ladder, movement and sandbox readers refuse raw files larger than **192 MiB (201,326,592 bytes)** before loading. The previous 128 MiB guard rejected existing uncapped sandbox captures; #230 measured those unchanged files at 153,697,015–171,889,880 bytes, with the three-capture analysis peaking at 4,048,093,184 committed bytes. Sandbox capture duration, frame rate and validation workload stay unchanged. No frames are skipped to satisfy the byte guard. Oversized input fails without an allocation result; use a shorter ladder diagnostic or a supported movement capture rate, and investigate oversized sandbox input without changing its timing check.

Each capture gets a sibling **`CAPTURE.raw-memory.txt`** containing `stage`, `capture_bytes`, `peak_working_set_bytes` and `peak_committed_bytes`, read inside Unity with Windows process counters. Successful analysis requires both peaks below **16,000,000,000 bytes (16 GB)** and fails if counters are unavailable or zero. `before_load` only reports context; the budget is enforced after analysis. These are process-lifetime high-water marks, so later captures in a multi-capture job include earlier work. The budget check happens after loading and cannot interrupt native expansion; the byte guard is the protection before loading. Failed analysis releases frames and attempts an `analysis_incomplete` memory record without replacing the original error.

Keep the raw captures and memory files locally for QA. Development captures are not ladder measurements.
